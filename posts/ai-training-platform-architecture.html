理解小模型训推平台：Go-Zero与Docker

约 10 分钟·Lulu Lennon

你平时写 train_runner.py、infer_runner.py，关心的只是模型、数据集和指标。但这份代码最终是怎么在平台上跑起来的？任务是怎么被调度的？为什么环境永远不会乱？

这篇文章用一个统一的例子把整条链路串起来：基于 Go-Zero 微服务搭建的小模型训推平台。目标是看完就能看懂我们这套标注 / 训练 / 评测平台的骨架，不需要深挖底层代码。

先认识四个核心角色

角色是什么类比
Go-Zero Go 语言微服务框架，用来写平台的「调度管家」：接收前端请求、管理任务状态、下发指令。它本身不跑模型训练。 项目经理——只派活、盯进度、记录结果，不亲自写训练代码。
镜像（Image） 一份静态只读的环境模板，打包好「Python + Torch + 训练脚本 + 全部依赖」。 标准化的「训练工作站装机 U 盘」——预装所有软件，只读、可复制分发。
容器（Container） 镜像启动之后正在运行的隔离实例。一个镜像可以同时变出很多个容器，互不干扰。 用这个 U 盘启动起来的一台独立工作站，用完可以关机销毁。
Runtime（运行时） 程序跑起来的整套环境：Python 解释器、torch、GPU 驱动、文件系统、进程资源。 工作站开机之后，一切能让代码跑起来的东西。

平台架构总览

自上而下四层：前端负责交互，Go-Zero 集群负责调度，Docker 引擎负责按镜像创建容器，外部存储负责保存产物。

提交一次训练任务，整条链路会发生什么

  1. 你在前端页面填写训练参数，提交任务。
  2. 请求发到 Go-Zero 的 Training 服务（调度管家）：
    • 校验参数，在数据库新建一条任务记录，状态标记为「待运行」；
    • 调用 Docker 引擎接口，下发指令：使用镜像 ai-runner:v1 启动一个容器。

    到这里 Go-Zero 的活就干完了——它不执行任何训练代码，只负责调度和状态管理。

  3. Docker 引擎找到静态镜像 ai-runner:v1，实例化出一个容器：
    • 镜像底层是只读层，所有训练容器共享这一份模板，不会重复拷贝 torch 这类大依赖；
    • 给这个容器单独分配一层薄薄的可读写层（upperdir）。
  4. 容器启动，进入 Runtime，执行 python train_runner.py：读代码、加载数据集、前向反向传播、训练模型。
    • ✅ 绝大多数写操作：新增训练产物（权重 ckpt、日志、评测指标）；
    • 👉 工程规范：产物不要写进容器自带的读写层，而是挂载外部存储卷，防止容器销毁后数据丢失；
    • 少量隐式写：Python 自动生成的 pyc 缓存、临时文件。
  5. 训练跑完，脚本把最终结果写入数据库；Docker 停止并销毁这个容器。
    • 容器的读写层跟着消失；
    • 原始镜像 ai-runner:v1 完好无损，可以继续跑下一批任务。
  6. 前端通过 Result 服务查询数据库，展示训练指标、下载模型。

算法同学最容易疑惑的四个点

1. 镜像 vs 容器：类和实例

镜像是蓝图，静态、只读、不占 CPU 内存；容器是这份蓝图跑起来的运行实例。同一个 ai-runner:v1 镜像可以同时启动 N 个训练容器，并行跑多组实验——环境完全一致、互不干扰。

底层原理：OverlayFS + 写时复制。 镜像的依赖文件是共享只读层，容器启动时不会复制一整份 torch 环境； 只有修改镜像内部原有文件时，才会把这个文件单独拷贝到容器的读写层。 正常训练场景几乎不会修改镜像内的脚本，写操作基本都是新增产物文件。

2. Go-Zero 是干嘛的？为什么不直接跑 Python？

  • 算法同学的 Python 脚本是计算负载：一次性任务，跑完就结束；
  • Go-Zero 微服务是平台控制面：常驻后台，负责接收请求、权限、任务排队、状态管理、结果查询。

拆开的好处：训练任务可以弹性扩缩容，推理压力大就多开推理容器；某个服务挂了（比如数据集服务），不会影响正在跑的训练。

3. Runtime 到底是什么？

就是容器里面让你的 train_runner.py 能正常跑起来的全部环境：Python 版本、torch、CUDA、依赖包、环境变量、文件目录。Docker 镜像存在的意义，就是把这套 Runtime 打包固定下来，解决那个经典问题：「本地能跑，服务器环境不一致跑不起来」。

4. 「写操作」到底写在哪里？

  • ✅ 绝大多数写：产出新文件（模型权重、日志、预测结果）；
  • ⚠️ 少量隐式写：Python 缓存、系统临时文件；
  • ❌ 正常实验流程不会修改镜像里原始的 train_runner.py，也就不会触发写时复制。

常见误区 Q&A

Q1：每跑一个训练任务，就要复制一份几十 G 的 torch 环境吗？

不是。镜像层共享，多个容器共用同一份依赖，磁盘只存一份，容器启动也很快。

Q2：容器删掉，训练好的模型权重就没了？

看写在哪。写在容器内部读写层会丢；挂载外部存储卷，产物独立保存，不受容器生命周期影响。

Q3：Go-Zero 里面有训练代码吗？

没有。Go-Zero 只负责调度，训练代码全部放在独立镜像里，在临时容器中运行。

Q4：我改了 train_runner.py，正在跑的容器会受影响吗？

不会。需要重新 build 出新镜像，新任务才会用上新版本；正在运行的容器使用的是启动时的镜像快照。

一句话总结

Go-Zero 是平台的调度大脑，Docker 镜像是固定好的算法环境包，容器是每次实验临时启动的隔离运行环境，Runtime 是脚本跑起来需要的整套依赖。你的训练脚本在容器的 Runtime 里执行，产出的模型和数据放到外部存储——容器用完即毁，环境永远不乱。
